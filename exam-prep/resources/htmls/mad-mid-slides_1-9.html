Unit 1Slides · Mobile landscape

Mobile apps, Flutter architecture, and setup

Native Android and iOS apps traditionally use different languages and platform APIs. Cross-platform approaches share more code, but make different trade-offs in user-interface rendering, platform access, performance, and development workflow.

The Flutter picture to remember 
Dart source
    ↓
Flutter framework (widgets, Material/Cupertino, animation)
    ↓
Flutter engine (rendering, text, Dart runtime)
    ↓
pixels on the screen

Flutter normally draws its interface through its own rendering stack rather than translating each Flutter widget into a native UI widget. This supports a consistent interface across platforms. Platform-specific APIs are still available through plugins/platform channels.

ApproachUseful distinctionTrade-off to explain
NativePlatform’s own language, UI toolkit, and APIsBest direct platform integration; separate platform work may be needed
FlutterDart + Flutter framework/engine draws the UIShared UI and consistent rendering; platform-specific work may still be needed
Bridge-based cross-platform UIShared-language code communicates with native componentsMore native look/integration, with a bridge/runtime in the architecture

Project anatomy and the command flow

lib/main.dart       app entry point and widget tree
pubspec.yaml       package dependencies and assets
android/ ios/      platform-specific project files

flutter create app_name
cd app_name
flutter run
flutter analyze

In Flutter, main() is the Dart entry point. runApp() attaches the root widget and starts rendering. Hot reload applies many code changes while keeping the running app state; it is not the same as restarting the app or rerunning all initialization.

Exam framing

If asked to describe Flutter, state the language, framework/engine rendering idea, and one trade-off. Avoid the inaccurate blanket claim that Flutter has no access to native APIs.

Unit 2Slides · Dart fundamentals

Dart syntax, types, null safety, and control flow

Dart is statically typed and uses sound null safety. A non-nullable type such as String cannot hold null; a nullable type such as String? can.

void main() {
  final String course = 'MAD';     // assigned once
  var count = 3;                    // inferred as int; variable can change
  const double tax = 0.05;          // compile-time constant
  String? nickname;                 // may be null

  print(nickname ?? 'Guest');       // fallback if null
  print(nickname?.toUpperCase());   // call only if non-null
  // nickname!.toUpperCase();       // assert non-null; can throw at runtime
}
SyntaxMeaningWhen it is useful
finalSet once at runtimeValue known only when code runs, but should not be reassigned
constCompile-time constantKnown constant values and constant Flutter widgets
T?Nullable TAbsence is a valid state and must be handled
??Use the right operand only when left is nullSafe default value
?.Null-aware member accessSkip a member call when the receiver is null
!Non-null assertionOnly when non-null is guaranteed; wrong assumptions fail at runtime

Small operators that show up in output questions

7 / 2   // 3.5: double division
7 ~/ 2  // 3: integer (truncating) division
7 % 2   // 1: remainder
x is String     // runtime type test
x is! String    // negated type test

Be able to trace if/else, loops, interpolation ('Hello $name'), and simple comparisons without mentally skipping a line. Dart collection literals infer types from their values in common cases.

Null-safety traps
  • String? s; is not the same as String s = '';.
  • s ?? 'none' does not replace an empty string; it replaces null.
  • s! does not safely convert null. It says “trust me,” and a wrong guess raises a runtime error.

Unit 3Slides · Functions and collections

Functions, collections, errors, and async

Function signatures and callbacks

String greet(String name) => 'Hi, $name';   // arrow function

void log(String message, [int level = 1]) { // optional positional
  print('$level: $message');
}

void show({required String title, int copies = 1}) { // named
  print('$title × $copies');
}

void applyToBooks(List<String> books, bool Function(String) keep) {
  print(books.where(keep).toList());
}

Positional arguments are matched by order. Named arguments are called by name; required means the caller must supply that named argument. A closure is a function that can retain access to variables from the scope where it was created.

int Function() makeCounter() {
  var count = 0;
  return () => ++count; // returned function remembers count
}
final next = makeCounter();
next(); // 1
next(); // 2

Collection operators: know the result shape

MethodWhat it doesShape/result
mapTransforms each elementIterable of transformed values; often call .toList()
whereKeeps elements matching a predicateFiltered iterable; often call .toList()
reduceCombines elements using the first element as the initial accumulatorOne value; no explicit initial value, so the collection must be non-empty
foldCombines from a supplied starting valueOne value; works naturally with a chosen initial value
sortOrders a list in placeMutates the receiver; copy first to preserve original
SetStores unique valuesSupports union, intersection, and difference
MapStores key → value pairsLook up by key, e.g. stock[title]
final nums = [1, 2, 3, 4, 5];
nums.where((n) => n.isEven).toList(); // [2, 4]
nums.fold(100, (sum, n) => sum + n); // 115

final sorted = [...nums]..sort();   // sort a copy
final unique = <String>{'Dart', 'Dart', 'Flutter'}; // {'Dart', 'Flutter'}
fold
items.fold(0,
  (sum, item) => sum + item.price)

Explicit starting value; can produce a different result type.

reduce
items
  .map((x) => x.price)
  .reduce((a, b) => a + b)

Starts at the first item; empty input is a problem.

Exceptions and asynchronous work

try {
  final amount = int.parse(text);
  print(amount);
} on FormatException catch (error) {
  print('Invalid number: $error');
} finally {
  print('This cleanup/reporting step runs either way.');
}

Future<String> loadName() async {
  final name = await fetchName();
  return name;
}

async makes a function return a Future. await waits for the future’s value inside an async function. Without await, code receives a Future object rather than the resolved value. Handle errors around the awaited operation; do not assume asynchronous work has already completed.

Unit 4Slides · Object-oriented Dart

Classes, constructors, and data encapsulation

A class describes fields and behavior; each instance has its own instance state. Constructors initialize that state and can enforce valid object creation.

class MenuItem {
  final String name;
  final int price;

  const MenuItem(this.name, this.price);
  MenuItem.free(this.name) : price = 0;

  factory MenuItem.fromCode(String code) {
    if (code == 'WATER') return MenuItem.free('Water');
    return MenuItem(code, 100);
  }
}
FeatureWhat to recognize/write
Field-formal parameterMenuItem(this.name, this.price) initializes fields directly
Named constructorMenuItem.free(...) offers another named construction path
Initializer listCode after : initializes final fields or asserts conditions before the constructor body
Factory constructorCan choose an existing instance or a subtype; it need not create a fresh object directly
GetterComputed/readable property, e.g. int get total => price * quantity;
SetterControlled assignment through a method-like property; store data separately (often in _balance)
staticBelongs to the class, not each object

Encapsulation and a safe setter

class Wallet {
  int _balance = 0;

  int get balance => _balance;
  set balance(int value) {
    if (value < 0) throw ArgumentError('balance cannot be negative');
    _balance = value;
  }
}
Constructor and setter pitfalls
  • An initializer list runs before the constructor body. It cannot read another instance field as though the new object were already fully initialized; use constructor parameters or a factory when appropriate.
  • Do not name a setter the same as a backing field and assign to itself: set width(v) { width = v; } recurses. Keep backing storage separate, such as _width.
  • A final field cannot be reassigned after initialization.

Unit 5Slides · OOP relationships

Inheritance, contracts, mixins, and enums

Three Dart class relationships are easy to confuse. Learn the exact difference, then practise applying the right relationship to a short scenario.

SyntaxMeaningMethod bodiesMultiple?
extends ASubclass inherits from one superclassInherits ready-made implementations; can overrideOne superclass
with MMixes reusable behavior into a classReceives concrete mixin behaviorCan list multiple mixins
implements APromises to provide a type’s interfaceMust implement all required instance membersCan implement multiple interfaces
abstract class Animal {
  void move();
  String sound() => '...';
}

mixin CanFly {
  void fly() => print('flying');
}

class Bird extends Animal with CanFly {
  @override
  void move() => print('flap');
}

class Plane implements CanFly {
  @override
  void fly() => print('propellers on');
}

An abstract class cannot be instantiated directly and can declare a contract plus shared implementation. An interface is a promise about available members. In Dart, every class also defines an implicit interface; implements does not inherit method bodies.

More OOP tools from the slides and labs

  • super and @override: call parent behavior where needed and explicitly mark a replacement method.
  • Enums: define a fixed set of choices. Enhanced enums may have fields, constructors, and methods; use values to inspect all choices.
  • Extensions: add helper methods to an existing type without changing or subclassing it.
  • Equality: if custom == is defined, also implement hashCode consistently when values are used in sets/maps.
  • static: class-level counters/helpers; the lab uses a constructor counter and a shared fee cap as examples.
Match the scenario

Bird and Plane need the same fly() implementation but do not share an “is-a” parent → a mixin fits. A class that must offer a capability but has its own implementation → use an interface/ implements. A Cat that is an Animal → inheritance / extends.

Unit 6Slides · Breaking into Flutter

Flutter widgets, state, and lifecycle

Flutter UI is a tree of widgets. Widgets are immutable descriptions of the interface. State that can change over time lives in a State object, not in mutable fields on a widget.

void main() => runApp(const MyApp());

class Greeting extends StatelessWidget {
  const Greeting({super.key});
  @override
  Widget build(BuildContext context) => const Text('Hello');
}

class Counter extends StatefulWidget {
  const Counter({super.key});
  @override
  State<Counter> createState() => _CounterState();
}

class _CounterState extends State<Counter> {
  int count = 0;
  @override
  Widget build(BuildContext context) => Text('$count');
}

Use StatelessWidget when the widget’s output depends only on its inputs and context. Use StatefulWidget when it owns local mutable state or lifecycle work. A stateful widget is the immutable configuration; its paired State<T> object holds the changing data.

Why and how setState works

onPressed: () {
  setState(() {
    count++;
  });
}

Changing a variable by itself does not ask Flutter to redraw. setState marks that state as changed and schedules a rebuild. The state change belongs inside its callback. A rebuild does not mean every object in the app is recreated from scratch.

Lifecycle order for a timer-backed State

State created
   ↓
initState()       once; call super.initState() first
   ↓
build()           may run many times
   ↓
timer callback → setState() → another build()
   ↓
dispose()         cancel timer; call super.dispose() last
late final Timer _timer;

@override
void initState() {
  super.initState();
  _timer = Timer.periodic(const Duration(seconds: 1), (_) {
    setState(() {});
  });
}

@override
void dispose() {
  _timer.cancel();
  super.dispose();
}
Lifecycle traps
  • initState runs once for a State object; build can run repeatedly.
  • Do not start a recurring timer in build; rebuilding could create repeated timers.
  • Cancel subscriptions/timers in dispose so callbacks do not outlive the widget.
  • Call super.initState() first and super.dispose() last.

Unit 7Slides · Tree, composition, and keys

BuildContext, composition, and keys

Flutter reconciles new widget descriptions with the existing element tree. A build creates new immutable widget objects, but matching elements and their State can be retained. BuildContext identifies a widget’s location in that tree and is used to find inherited information and navigate among ancestors.

Composition over inheritance

Build a screen from small widgets that contain other widgets. Prefer combining reusable pieces (for example, a styled button inside a card) over making a deep custom subclass hierarchy just to share layout or appearance.

Why keys matter in reordered lists

Tile('A', key: const ValueKey('A')),
Tile('B', key: const ValueKey('B')),

setState(() {
  tiles = tiles.reversed.toList();
});

Without keys, Flutter generally matches same-type widgets by their position. When stateful tiles reorder, the existing State may stay with a slot rather than with the logical item. A stable key tells Flutter which child is which, so the tile’s tap count follows that item.

What you seeLikely explanation/fix
Tap count changes on the wrong tile after swappingAdd a stable identity key such as ValueKey(item.id) to each repeated stateful child
App shows new value after parent state changessetState triggered a rebuild and the widget tree was reconciled
Need access to a theme, navigator, or inherited valueUse the appropriate API with the relevant BuildContext
Key quality matters

Use a key derived from stable item identity, not the current index when items can reorder. A unique key is only helpful if it remains attached to the same logical item.

Unit 8Slides · Widgets, layout, and navigation

Row, Column, flex, Stack, and Container

Flutter layout follows constraints: parents pass constraints down, children choose a size within them, and parents position children. A Row lays out horizontally; a Column vertically. Main-axis and cross-axis meanings rotate with the widget.

WidgetMain axisCross axis
RowHorizontal (left ↔ right)Vertical (top ↕ bottom)
ColumnVertical (top ↕ bottom)Horizontal (left ↔ right)

Alignment and flexible space

  • MainAxisAlignment.start packs children at the beginning; end at the end; center centers them.
  • spaceBetween puts the first and last child at the ends and divides the remaining gaps between children.
  • Expanded(flex: n) takes a tight share of the remaining main-axis space. Flex values are weights, not pixel widths.
  • Flexible lets its child use its share but can allow it to be smaller; Expanded is the tight-fit form.
Row(children: [
  const SizedBox(width: 100),
  Expanded(flex: 1, child: X()),
  Expanded(flex: 2, child: Y()),
])

available width = 400 - 100 = 300
total flex = 1 + 2 = 3
X = 300 × 1/3 = 100 px
Y = 300 × 2/3 = 200 px

Overlay and decoration

Stack(
  children: [
    const SizedBox(width: 300, height: 120),
    const Positioned(
      top: 10,
      right: 20,
      child: Icon(Icons.star, size: 24),
    ),
  ],
)

For a 300-pixel-wide Stack and a 24-pixel-wide icon, right: 20 gives a left edge of 300 − 20 − 24 = 256 px. top: 10 gives a top edge of 10 px. Positioned must be a child of a Stack.

Container uses padding inside its child and margin outside its box. If using decoration: BoxDecoration(...), set the color in the decoration. Do not provide both color: and decoration: to the same Container.

Common layout repairs
  • Long text in a Row overflows → wrap a text child with Expanded or Flexible, or choose a scrollable/wrapping layout.
  • Expanded outside a Row, Column, or Flex → wrong parent/constraint context.
  • Use SizedBox for a simple fixed gap; do not add a heavier widget when a gap is all you need.

Navigation vocabulary from the slide set

A route is a screen destination. A router can map a path (including a parameter such as :id) to a screen. Distinguish replacing/navigating to a destination from pushing a new page onto a navigation stack; know the behavior used in the course example if a question names a specific API.

Unit 9Slides · State management and REST

Shared state, Riverpod, REST, and JSON

setState is local to one State object. When independent screens must see and update the same cart/counter, shared state avoids duplicating unrelated copies or threading values through many layers.

ApproachCore ideaCourse example
Local setStateState owned by one widget’s State objectCounter screen
Lift state upMove shared state to a common ancestor and pass data/callbacks downWorks for a modest tree; can create prop/callback chains
RiverpodProvider exposes shared state/actions; consumers read or watch itProviderScope at app root; ref.watch to observe
// Shape of the Riverpod flow from the lecture:
ProviderScope
  └─ ConsumerWidget.build(context, ref)
       ├─ ref.watch(provider)   // read + rebuild when it changes
       └─ ref.read(provider.notifier).action() // perform an update

ref.watch subscribes the widget so it rebuilds when the provider value changes. ref.read is commonly used to access an action without subscribing in that expression. Provider APIs vary by provider type; follow the exact package/API version shown in your project/lab.

REST request → response → UI

HTTP request (method + URL)
        ↓
REST API response (status + JSON body)
        ↓ decode JSON
Dart Map / List / model
        ↓
UI: loading → data OR error
  • GET retrieves a resource; the response body is not automatically a Dart model.
  • JSON objects decode to map-like values and JSON arrays to lists. Validate/convert values before using them as typed fields.
  • Model the async UI states explicitly: loading, success/data, and error (and empty data if relevant).
  • Do not start network requests on every rebuild without a lifecycle/future/provider strategy.

Answers that lose easy marks
  • Writing “mixin” without with when the blank asks for a keyword.
  • Putting initState after the first build, or forgetting to dispose resources.
  • Writing “Expanded can shrink” (it uses tight fit); that property belongs to Flexible’s loose fit behavior.
  • Giving only the line number or only the fix for a two-part bug question.
  • Computing a flex ratio from the full screen width instead of the leftover width.
  • Putting Positioned under a Row rather than inside a Stack.
  • Returning a Text from a widget question when the requested structure is a Row with the required children.
